# AGENTS

## Что мы делаем

- Собираем веб-прототип мобильной игры на TypeScript и Vite.
- Игровые механики и правила поведения интерфейса описаны в `gdd.md`.
- Карта проекта, структура модулей и основные команды находятся в `PROJECT.md`.
- Текущий визуал задают UI-код и стили. Отдельная спецификация пикселей не ведётся.

## Общение

- Всегда общайся с пользователем по-русски.
- Все вопросы, пояснения, отчёты о выполнении и сообщения об ошибках пиши по-русски.
- Имена файлов, идентификаторы в коде, команды, названия библиотек и API не переводи.
- Если пользователь задаёт вопрос, только ответь на него и не вноси изменения в проект.
- Если пользователь просит что-то сделать, стремись самостоятельно довести задачу до готового проверенного результата.

### Уточняющие вопросы

Не задавай вопросы автоматически перед каждой задачей.

Задавай уточняющие вопросы только если без ответа существует несколько существенно разных вариантов реализации и выбор нельзя надёжно определить из:

- запроса пользователя;
- существующего поведения игры;
- `gdd.md`;
- текущей архитектуры проекта.

Если уточнение действительно необходимо:

1. Сначала самостоятельно изучи минимально необходимый контекст.
2. Задай все известные на этот момент существенные вопросы одним сообщением.
3. Не спрашивай о технических деталях, которые можешь разумно решить самостоятельно.
4. После ответа пользователя продолжай работу без дополнительных вопросов, если новая критическая неоднозначность не появилась.

Не спрашивай разрешения на очевидные технические действия: изменение связанных файлов, добавление необходимых тестов, исправление обнаруженных ошибок и запуск проверок.

## Работа с контекстом

Главная цель — использовать минимальный объём контекста, достаточный для корректного выполнения задачи.

### Экономия лимитов

- Для локальных правок читай только конкретные функции, селекторы и небольшие диапазоны строк, непосредственно связанные с задачей.
- Не загружай повторно целые файлы, документы, скриншоты или выводы инструментов, если нужное содержимое уже известно и после этого не менялось.
- Не запускай сабагентов для локальных и однозначно расположенных изменений. Используй их только в случаях, явно перечисленных в разделе «Сабагенты».
- Никогда не проводи браузерную проверку без прямого указания пользователя. Если требование можно надежно проверить тестом, typecheck или сборкой, используй более дешевую проверку.
- При успешных тестах, typecheck и сборке не загружай полный вывод команды: достаточно статуса завершения и краткой сводки. Полный вывод изучай только при ошибке.
- При ошибке команды извлекай только относящийся к причине фрагмент вывода, а не весь лог.
- Не перечитывай все приложенные изображения после того, как их существенные требования уже зафиксированы. Для последующих правок используй только новый референс и непосредственно связанные ранее установленные правила.
- Предпочитай один целевой цикл «изменение → локальная проверка» нескольким повторным полным проверкам. Полный набор обязательных проверок запускай один раз перед завершением.

### Начало задачи

1. Сначала прочитай `PROJECT.md`.
2. По карте проекта определи затронутую систему.
3. Читай только файлы этой системы и непосредственно связанные с ними тесты.
4. Расширяй область чтения только если текущего контекста недостаточно.

Если нужный модуль уже однозначно указан в `PROJECT.md`, не выполняй дополнительное исследование структуры проекта.

### GDD

Не загружай целиком `gdd.md`, если задача не меняет игровые механики или правила поведения интерфейса.

При необходимости сначала найди поиском относящийся к задаче раздел и прочитай только его.

Если задача меняет механику или поведение интерфейса, обнови соответствующее актуальное описание в GDD.

GDD описывает только текущее состояние игры. Не добавляй туда историю изменений или причины предыдущих решений.

### Чтение кода

- Предпочитай поиск конкретных символов, функций, типов и селекторов чтению большого количества файлов.
- Не перечитывай без необходимости файлы, содержание которых уже известно в текущей сессии и которые после этого не менялись.
- Не загружай generated output, зависимости, build-артефакты и большие нерелевантные файлы.
- Не исследуй весь репозиторий «на всякий случай».
- Не пересказывай содержимое прочитанных файлов самому себе без необходимости.
- Если задача локальна, сохраняй её локальной.

## Сабагенты

Сабагенты используются для экономии контекста основной модели, а не как обязательный этап работы.

Не вызывай сабагента, если основная модель может быстро получить необходимую информацию из `PROJECT.md` и нескольких известных файлов.

Не создавай цепочки сабагентов.

Один сабагент не должен запускать других сабагентов.

### Explore

`Explore` — дешёвый read-only агент для поиска по локальному проекту.

Используй `Explore`, если:

- `PROJECT.md` не позволяет определить нужный код;
- неизвестно, где реализовано нужное поведение;
- одна механика потенциально проходит через много модулей;
- нужно найти все использования некоторого состояния, типа, события или функции;
- перед крупным изменением нужна компактная карта связей между несколькими системами.

Не используй `Explore`, если нужный файл уже очевиден из `PROJECT.md` или текущего контекста.

Формулируй задачу `Explore` узко.

Требуй от него короткий результат:

- какие файлы действительно относятся к задаче;
- какие функции, типы или состояния важны;
- как они связаны;
- какие места основной модели необходимо прочитать.

Не проси `Explore` подробно объяснять код или предлагать архитектуру, если это не требуется.

`Explore` не должен изменять файлы.

### Reviewer

`Reviewer` — read-only агент для дополнительной проверки рискованных изменений.

Не запускай `Reviewer` после каждой задачи.

Используй его после реализации, если изменение затрагивает:

- новую игровую систему;
- несколько существующих систем одновременно;
- архитектуру;
- сохранение или загрузку состояния;
- асинхронное поведение;
- таймеры и жизненный цикл;
- сложную синхронизацию состояния и UI;
- физику или collision logic;
- процедурную генерацию;
- трудный баг с неочевидной причиной;
- код, ошибка в котором может долго оставаться незаметной при обычной игре.

Для простых UI-правок, текста, числовых параметров, локальных изменений и реализации по существующему шаблону `Reviewer` не нужен.

Запускай `Reviewer` не более одного раза после обычной реализации.

Если `Reviewer` обнаружил конкретную существенную проблему, основная модель самостоятельно решает, как её исправить.

После исправления не запускай `Reviewer` повторно, если изменение не было существенно переработано.

`Reviewer` не должен редактировать файлы.

Основная модель всегда несёт окончательную ответственность за результат.

## Архитектура

- Сохраняй разделение игровой логики, состояния интерфейса и рендера.
- Новые числовые параметры размещай в `src/config.ts`.
- Игровые правила реализовывай в игровом слое, предпочтительно чистыми функциями.
- Новую UI-логику размещай в соответствующем модуле `src/ui`.
- Общие элементы выноси в общий модуль, не дублируй разметку, игровую логику и стили.
- Стили размещай в тематических файлах `src/styles`.
- Предпочтительный размер модуля — 150–350 строк.
- Если файл устойчиво превышает 400 строк и содержит несколько обязанностей, раздели его по смыслу.
- Не дроби связную логику на множество файлов без самостоятельной ответственности.
- Следуй существующим архитектурным паттернам проекта, если нет причины их менять.
- Не выполняй несвязанный с задачей рефакторинг.

## Графические ресурсы

- Персонажи, мебель и предметные слои ячеек создаются и редактируются как SVG. Не заменяй их PNG и не встраивай растровый рисунок в SVG вместо векторной геометрии.
- PNG используется для фонов и общих текстур, включая единую текстуру кирпича всех ячеек. Допустимы отдельные растровые иллюстрации, например картины на стене, и существующие иконки интерфейса.
- Существующие PNG-слои входа временно сохраняются до подготовки настоящей SVG-замены. Новые предметные ассеты следуют правилу SVG.
- В `public/art/` хранятся только используемые приложением ресурсы. Общие текстуры и поверхности находятся в `public/art/shared/`; не копируй их в папки отдельных ячеек.
- Рабочий SVG в `public/art/` — единственная редактируемая версия ассета. Уникальные исходные композиции и резервные ракурсы находятся в `art/sources/`, визуальные референсы — в `art/references/`, полезные промпты — в `art/prompts/`.
- Пути SVG карты и порядок частей персонажей задаются в `src/ui/map-assets.ts`, числовые точки крепления — в `src/config.ts`. Сохраняй разделение фона, мебели и частей персонажа для правильных перекрытий и анимации.
- SVG отдельных предметов и частей персонажей использует `viewBox` от `0 0` и встроенные размеры в пикселях сцены. Якорь — центр нижнего края. Общие поверхности могут растягиваться по ширине ячейки.
- Не сохраняй производные предпросмотры и не добавляй сборщик предпросмотра в проект. Показывай рабочий SVG напрямую; временные композиции для просмотра создавай вне репозитория.
- Удаляй неиспользуемые определения внутри SVG только после проверки ссылок `href` и `url(#...)`. При встроенном SVG изолируй идентификаторы определений разных экземпляров.

## Реализация

Сначала пойми существующее поведение, затем вноси изменение.

Не создавай новую абстракцию, если существующая архитектура уже предоставляет подходящий механизм.

Для похожего поведения сначала найди существующую реализацию и следуй её паттерну.

Не расширяй область задачи дополнительными улучшениями, которые пользователь не просил и которые не нужны для корректности результата.

Если во время работы обнаружен очевидный баг, непосредственно вызванный изменяемым кодом, исправь его без отдельного согласования.

Если обнаружена отдельная несвязанная проблема, не исправляй её в рамках текущей задачи.

## Документация

При изменении механики или поведения интерфейса обновляй соответствующий раздел `gdd.md`.

Не дублируй в документации значения размеров, цветов, отступов и других визуальных параметров, уже заданных в коде.

При изменении структуры проекта обновляй `PROJECT.md`.

Не обновляй документы, которых задача фактически не касается.

Не записывай в проект историю работы агента.

## Тесты

При изменении игровой логики добавляй или обновляй тесты. Тесты покрывают правила и наблюдаемое поведение игрового слоя, а не визуал интерфейса.

Размещай тест рядом с предметной областью в отдельном файле `tests/<system>.test.ts`; не собирай несвязанные системы в общий монолитный файл.

Предпочтительный размер тестового файла — до 400 строк. Если файл устойчиво превышает этот размер и проверяет несколько сценариев или подсистем, раздели его по смыслу.

Детерминированный random, создание типового состояния и повторяющиеся этапы подготовки выноси в `tests/support.ts` или тематический helper.

Одинаковые правила для нескольких территорий, типов ресурсов или уровней оформляй табличными тестами вместо копирования сценариев.

Проверяй наблюдаемое поведение и публичные функции игрового слоя.

Конфиг (`src/balance.json`, `src/config.ts` и определения игровых сущностей) — источник истины параметров. Не хардкодь в тестах его значения, количество или порядок элементов, цены, награды, цели, длительности и списки разблокировок. Удаляй тесты, которые только повторяют содержимое конфига. Проверяй игровую логику с данными из конфига: списание цены, выдачу награды, достижение цели, применение разблокировок и ограничения. Фиксированные числа допустимы для независимых тестовых входных данных и правил, не заданных конфигом.

Не добавляй тесты исходного текста UI-модулей, CSS-контрактов, размеров, цветов и других визуальных параметров.

Один тест должен проверять один связный контракт.

Для разных причин падения используй отдельные тесты, но не дублируй одинаковую подготовку состояния.

При работе с одной системой сначала читай соответствующий тестовый файл и необходимую часть `tests/support.ts`.

Не загружай весь каталог тестов, если задача не является сквозной.

## Проверка результата

Написанный код сам по себе не считается завершённой задачей.

Основная модель отвечает за проверку результата.

Используй самую дешёвую проверку, которая способна обнаружить вероятные ошибки, и переходи к более широкой только при необходимости.

### Во время реализации

Не запускай полный набор проверок после каждого небольшого изменения.

Сначала используй локальную или целевую проверку изменяемой системы, если она доступна.

Если проверка падает:

1. Изучи конкретную ошибку.
2. Исправь причину.
3. Повтори относящуюся к ней проверку.

Не загружай и не анализируй огромный вывод команды, если нужная ошибка находится в небольшой его части.

### Перед завершением изменения игровой логики

Обязательно выполни:

`npm.cmd test`

`npm.cmd run build`

Не считай задачу завершённой, если одна из этих проверок падает из-за внесённых изменений.

### TypeScript

Запускай `npm.cmd run typecheck`, когда изменение затрагивает типы, публичные интерфейсы, состояние, сигнатуры функций или несколько TypeScript-модулей и ошибка типов не гарантированно покрывается другими выполняемыми проверками.

### UI и gameplay

Если изменение влияет на непосредственно наблюдаемое поведение игры и доступна автоматизированная или браузерная проверка:

- запускай приложение;
- проверяй конкретно изменённый пользовательский сценарий;
- проверяй консоль на относящиеся к изменению ошибки;
- проверяй наиболее важные edge cases изменённой механики.

Не выполняй полный ручной обход всей игры после каждой небольшой задачи.

Для локальной UI-правки проверяй прежде всего затронутый экран или взаимодействие.

Для крупной gameplay-фичи проверяй основной happy path и наиболее вероятные пограничные сценарии.

Не добавляй тяжёлый новый тестовый или браузерный framework только ради проверки одной небольшой задачи.

## Завершение задачи

Перед ответом пользователю убедись, что:

- запрошенное поведение реализовано;
- необходимые документы синхронизированы;
- относящиеся к изменению проверки проходят;
- нет известной неисправленной регрессии, вызванной изменением.

Не описывай пользователю внутренний процесс рассуждений.

Финальный ответ держи коротким.

Сообщи:

- что в итоге сделано;
- какие существенные проверки выполнены;
- только те проблемы или ограничения, которые реально остались.

Если задача полностью выполнена и проблем нет, не добавляй лишних рекомендаций и длинных технических пояснений.
